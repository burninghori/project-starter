# PR 전 리뷰

## 범위 잡기

이 skill 은 **PR 로 올라갈 변경**(코드와, 같은 PR 에 담긴 문서·설정)의 리뷰 기준이다. 문서·설정 변경은 아래 체크리스트 중
규약 항목(CLAUDE.md 규칙, 문서 사이의 정합성)으로 본다. PR 과 따로 검토하는 설계안·명세 초안·계획의 리뷰는 대상에 맞게 따로 본다.
로컬 리뷰는 사용자가 요청할 때만 한다. 「리뷰해줘」는 메인 세션이 이 skill 로 직접 리뷰하고, 사용자가 리뷰 에이전트를 명시하면
`pr-reviewer`(`.claude/agents/pr-reviewer.md`)가 이 skill 로 리뷰한다 — 코드를 작성한 세션의 맥락 없이 diff·코드·규약만으로 보고 싶을 때다.

1. 대상 변경을 구한다. **커밋하지 않은 변경도 대상이다**(커밋은 사용자가 요청할 때만 하므로 PR 직전까지 미커밋일 수 있다).
   - 브랜치 커밋: `git diff main...HEAD --stat` 후 `git diff main...HEAD`. 다른 사람의 PR 이면 그 브랜치 기준.
   - 커밋하지 않은 변경: `git status --untracked-files=all` 과 `git diff HEAD`. 새 파일(untracked)은 diff 에 나오지 않으므로
     목록을 보고 직접 읽는다(`--untracked-files=all` 이 없으면 새 폴더 안의 파일이 폴더 이름으로만 보인다).
2. **바뀐 파일은 전부 읽는다**(diff 만 보지 않는다). 바뀐 심볼의 호출부와 테스트도 연다.
3. 관련 규약을 연다: CLAUDE.md, 바뀐 영역의 skill(`backend-conventions`, frontend/CLAUDE.md), 관련 결정 기록.
4. PR 본문의 「AI 리뷰」 칸을 본다. 「코드만」이면 문서 변경은 아래 경계의 규약 항목만 본다.

### 문서 변경의 경계

`frontend/docs/design/`(화면 기능 정의·목업·디자인 정의)·`docs/specs/`·`docs/decisions/` 의 변경은 **기획·설계 판단 자체를 평가하지 않는다.**
원본(시안·기획 자료·회의)은 저장소 밖에 있어 리뷰어가 볼 수 없고, 기획 반영은 메인 개발자의 역할이다(collaboration.md 1절).
문서 변경에서 보는 것은 저장소 안의 정합성뿐이다.

- 공통 어휘(CLAUDE.md 표)와 어긋나는 용어
- 결정 기록·명세·코드와 서로 다른 말(같은 값을 두 문서가 다르게 적음, 코드가 이미 다른 동작)
- 깨진 링크·경로, 규약 위반(문서 상단 작성자·날짜, 개인 계정명, 외부 고유 값)
- 명세의 형식 요건(결정 기록의 형식, 표의 칸 누락)

"이 기획이 맞나" 류의 의문은 지적이 아니라 요약의 **질문** 절에 분리해 적는다. 지적으로 올리지 않는다.

## 체크리스트

### 정확성 — 가장 먼저

- [ ] 요청한 기능이 실제로 동작하는가. 빠진 경로(빈 목록, 없는 ID, 권한 없음, 중복)가 있는가
- [ ] 업무 계산(합계·비율·상태 판단)이 CLAUDE.md 「도메인 원칙」 · 명세의 정의와 같은가
- [ ] 계산할 수 없는 경우를 그럴듯한 값으로 채우지 않았는가(기조 1)
- [ ] 의미 없는 기본값·optional·조용한 except 가 없는가(기조 5)
- [ ] 동시성: 같은 대상을 두 요청이 바꿀 때 결과가 맞는가(unique 제약, 상태 전이 검사)

### 구조와 경계

- [ ] 소유자가 있는 공통 영역(collaboration.md 소유 표 — 백엔드 공통 등)을 바꿨다면 별도 변경으로 분리됐는가
- [ ] 프론트 공통 부품을 새로 만들었다면 같은 용도의 기존 부품 · 다른 개발자의 열린 PR 과 겹치지 않는가, PR 본문에 「공통 부품 추가」를 적었는가
- [ ] 기획 문서를 고쳤다면 PR 본문에 「기획 보완: 문서 · 절 — 무엇」을 적었는가
- [ ] 공통 테이블을 바꿨다면 결정 기록이 있는가
- [ ] 마이그레이션: 순번이 main 다음인가, 머지된 파일을 고치지 않았는가, autogenerate 결과를 손봤는가, 모델과 일치하는가
- [ ] 등록 지점(router·model_registry·pages-config)은 한 줄 추가만인가
- [ ] 로직이 라우터가 아니라 서비스에 있는가. 화면이 `fetch` 를 직접 부르지 않는가

### 계약

- [ ] 오류는 `SemanticHTTPException(code=...)`, code 는 `<대상>_<사유>`, 사용자 문구를 backend 에 넣지 않았는가
- [ ] 새 code 를 만들었다면 같은 뜻의 기존 code 가 없는가. 목록·생성 파일·`error-messages.ts` 문구가 같은 변경에 있는가
- [ ] 요청 모델이 `ApiRequestBase`, 응답이 `ApiBase` 인가. 목록은 `PageEnvelope` 인가
- [ ] 화면 타입이 실제 응답(camelCase)과 같은가

### 화면

- [ ] 목업의 배치·문구를 그대로 옮겼는가. 디자인은 app-ui 클래스·토큰으로만 그렸는가(색 리터럴·임의값 없음)
- [ ] 로딩·오류·빈 상태가 모두 있는가. 오류에 요청 ID 가 보이는가
- [ ] 계약이 없는 자리는 `PendingContract` 로 남겼는가(지우거나 지어내지 않았는가)
- [ ] 화면 문구가 공통 어휘와 같은가

### 테스트·검사

- [ ] 새 로직에 테스트가 있는가(업무 규칙은 표 형태로 촘촘히). 오류 경로 테스트가 있는가
- [ ] verify skill 의 검사를 돌렸고 결과를 PR 에 적었는가. 못 돌린 것을 통과로 쓰지 않았는가

### 운영·보안

- [ ] 실패 사유가 로그나 응답에 남는가. 비밀 값이 로그·응답·코드에 없는가
- [ ] 새 설정 값이 `.env.example`·`.env.test`·(필요하면) 배포 설정에 반영됐는가
- [ ] 상태를 바꾸는 동작을 GET 으로 만들지 않았는가(출처 검사 · CSRF 방어는 쓰기 메서드만 본다 — api.md 「인증 계약」)
- [ ] 주석이 현재 동작을 맞게 설명하는가. 낡은 주석·죽은 코드가 남지 않았는가

## 보고 형식

지적마다 **심각도 · 위치(`파일:줄`) · 문제 · 근거 · 제안**을 쓴다. 심각도 순으로 정렬한다.

| 심각도 | 뜻 |
|---|---|
| 차단 | 잘못된 결과·데이터 손상·보안 문제·규약의 핵심 위반. 머지 전에 반드시 고친다 |
| 권장 | 유지보수·일관성 문제. 이번에 고치는 게 낫다 |
| 참고 | 취향·대안 제시. 무시해도 된다 |
| 질문 | 기획·설계 의도를 모르면 판정할 수 없는 것. 지적이 아니라 작성자에게 묻는다 |

- 확인하지 못한 추측은 지적으로 쓰지 않는다. 의심이면 "확인 필요"로 표시하고 무엇을 보면 판정되는지 적는다.
- 문제가 없으면 "지적 없음"과 함께 **무엇을 봤는지**(읽은 파일, 확인한 경로)를 적는다.
- 자기 변경을 리뷰한 경우, 차단·권장 지적을 고친 뒤 verify 검사를 다시 돌린다. 차단 지적을 고쳤으면 고친 부분만 한 번 다시
  리뷰한다. 권장 지적은 고친 뒤 재리뷰 없이 마친다.

## GitHub 자동 리뷰로 돌 때

`.github/workflows/ai-review.yml` 이 PR 이 열릴 때 이 skill 로 리뷰한다(PR 당 한 번, 재실행은 PR 코멘트 `/review`, 제외는 라벨
`skip-ai-review`). 그 실행에서는 보고 형식을 GitHub 에 맞춘다.

- 줄 단위 지적은 인라인 코멘트로, **PR diff 안의 경로·줄에만** 단다(diff 밖은 GitHub 이 거부한다). diff 밖 지적은 요약의 별도 절에.
- 요약은 실행이 만든 추적 코멘트 하나를 갱신해 남긴다. 새 PR 코멘트를 만들지 않는다. 마지막 행동은 그 코멘트 마감이다.
- 읽기 도구와 코멘트 게시만 허용된다. 코드를 고치지 않는다(`pr-reviewer` 에이전트와 같은 제한).

## 리뷰 에이전트로 리뷰할 때 — 부르는 쪽(메인 세션)이 할 일

1. `pr-reviewer` 를 부르며 변경 의도와 verify 검사 결과(돌린 명령·결과, 못 돌린 것)를 넘긴다.
2. 에이전트 지적은 틀릴 수 있다. 코드로 직접 확인해 맞는 것만 반영하고, 틀린 지적은 근거와 함께 사용자에게 보고한다.
3. 리뷰 뒤 `git status` 와 diff 가 리뷰 전과 같은지 확인한다. 에이전트의 Bash 제한은 지시일 뿐 강제가 아니다.
4. 재리뷰는 위 보고 형식의 규칙을 따른다.

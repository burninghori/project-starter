# 협업 방식 — 개발자 여러 명 × 각자의 AI

여러 개발자가 각자 Claude Code 로 개발한다. 사람 여럿, AI 여럿이 같은 저장소를 고치므로 **규칙은 저장소 문서에만 두고**,
백엔드 공통 영역에는 **소유자**를 두고(프론트 영역은 인증 · 권한을 빼고 소유자 없이 함께 고친다 — [결정 0001](../decisions/0001-기능별-풀스택-분담.md)), 머지 전에 **AI 리뷰 + 사람 리뷰**를 거친다. 이 문서는 그 방법을 정한다.

## 1. 분담 — 기능별 풀스택

백엔드/프론트엔드로 나누지 않고 **기능(도메인) 단위로 나눠 한 사람이 DB·API·화면·테스트를 끝까지** 만든다([결정 0001](../decisions/0001-기능별-풀스택-분담.md)).

- 프론트를 한 사람에게 몰지 않고 모두 같은 디자인 정의·공통 컴포넌트를 AI 에 참조시킨다.
- API 명세를 기다리는 시간이 없다. 기능 담당자가 API 와 화면을 함께 정한다.
- 메뉴 단위로 완성된다 — 메뉴는 처음부터 보이고, 기능이 완성되는 PR 이 그 메뉴를 「준비 중」에서 연다([결정 0003](../decisions/0003-메뉴는-처음부터-모두-보이고-화면이-없는-메뉴는-준비-중-화면으로-연다.md)).

### 역할

| 역할 | 하는 일 |
|---|---|
| 메인 개발자(리드) | 기반(저장소 구조·실행 환경·공통 모듈·규약), DB 스키마·마이그레이션 체인, 백엔드 공통 영역, 주요 설계·작업 배분, 기획 반영(기획 자료를 명세·화면 정의로 옮기기) |
| 개발자 | 배분받은 기능을 풀스택으로. 화면을 만들며 생기는 기획 문서의 세부 보완(문구 · 빈 상태 · 기획과 다르게 가는 이유)은 그 화면을 만드는 사람이 같은 PR 에서 고친다 |

누가 어느 역할인지는 [CLAUDE.md 「git」](../../CLAUDE.md#git) 의 개발자 표에 적는다.

### 진행 순서

기반은 **메인 개발자가 먼저 만들고**, 그 위에서 기능을 나눈다. 모두가 같은 계약(스키마·API 규칙·레퍼런스 구현)에서
출발해야 이후 나눠 만든 결과가 같은 모양이 된다.

| 단계 | 누가 | 하는 일 |
|---|---|---|
| ① 골격 | 메인 개발자 | 이 시작 저장소를 프로젝트에 맞게 바꾼다(README 「새 프로젝트 시작 시 바꿀 것」) — `make verify` 통과 |
| ② 정의 | 메인 개발자 | [DB 스키마 정의](../specs/db-schema.md)(공통 테이블 우선), [API 명세](../specs/api.md), 기능 목록과 분담 확정, 결정 기록 |
| ③ 개발 | 모두 | 기능 하나 = Issue 하나, PR 은 리뷰할 수 있는 크기로 나눈다(6절). 처음 머지되는 기능(API 구조 · 화면)이 레퍼런스가 되므로 서로 리뷰하며 맞춘다 |

다른 개발자는 ①~② 동안 [로컬 개발 환경 세팅](local-setup.md)을 마치고, 규약 문서와 ② 정의를 리뷰하며 합류를 준비한다.
②에서 정의한 공통 테이블·API 규칙을 ③에서 바꿔야 하면 먼저 명세와 결정 기록을 고친다.

기능 분담 표에는 번호·날짜·공수·진행을 적지 않는다 — 일정과 진행은 GitHub Project 의 로드맵과 마일스톤의 Issue 로 본다.

## 2. 공통 영역 소유

백엔드 공통 영역마다 **소유자 한 명**을 둔다. 소유자는 그 영역의 변경을 리뷰하고 모양을 지킨다. 소유자가 아닌 사람도 고칠 수 있지만
**그 변경만 작은 별도 PR** 로 먼저 올리고 소유자 리뷰를 받는다. 기능 PR 에 소유자가 있는 공통 영역의 변경을 섞지 않는다.

**프론트 영역은 인증 · 권한(아래 표)을 빼고 소유자가 없다**([결정 0001](../decisions/0001-기능별-풀스택-분담.md)) — 화면 단위로 풀스택 개발을 하므로 공통 컴포넌트 · 디자인 시스템 · 셸도 화면을 만드는
사람이 기능 PR 안에서 함께 고친다. 대신 같은 용도의 공통 부품이 둘 생기지 않게, 공통 부품(`components/` · `lib/` · `styles/` 의
공용 클래스 · `api/` 의 공용 타입)을 **새로 만들 때는 다른 개발자의 열린 PR 에 같은 용도가 있는지 먼저 확인하고, PR 본문에
「공통 부품 추가: 무엇」을 적는다.** 리뷰어가 그 줄로 중복을 본다.
기획 문서를 고쳤으면 **PR 본문에 「기획 보완: 문서 · 절 — 무엇」을 적는다.** 화면 동작 · 문구 · 범위가 바뀌는
보완이면 메인 개발자가 그 줄로 확인한다(메인 개발자가 쓴 PR 이면 다른 리뷰어가 본다).

| 영역 | 경로 | 소유자 |
|---|---|---|
| DB 스키마 · 마이그레이션 체인 | `backend/migrations/`, 공통 테이블 모델 | 메인 개발자 |
| 백엔드 공통 | `backend/app/{api,db,middleware,core,worker}/`, `app/{config,logging,main}.py` — 인증 미들웨어는 예외(아래 행) | 메인 개발자 |
| 인증 · 권한 | `backend/app/domains/auth/`, `app/middleware/auth.py`, 프론트의 인증 상태·로그인 화면·401 처리 | 담당자: (프로젝트 시작 때 지정) |
| 기획 문서 | 화면 기능 정의 · 목업 원본(프로젝트에서 `frontend/docs/design/` 아래에 둔다) | 없음(모두 작업 — 화면을 만들며 하는 세부 보완은 각자, 새 기획 · 시안 결정을 옮기는 일은 메인 개발자, 1절) |
| 프론트 공통 컴포넌트 · 디자인 시스템 | `frontend/src/{components,styles,lib}/`, `frontend/docs/design/` 의 디자인 정의(design-concept · app-shell-spec · app-ui-spec) | 없음(모두 작업 — 새 공통 부품은 위 확인 · 기재) |
| 프론트 셸 · 라우팅 · API 전송 계층 | `frontend/src/app/{shell,routing}/`, `frontend/src/api/transport.ts` | 없음(모두 작업 — `transport.ts` 의 401 · 세션 만료 처리는 위 인증 · 권한 행) |
| 공용 규약 | `CLAUDE.md`, `frontend/CLAUDE.md`, `.claude/`, `docs/development/` | 모두(변경은 작성자가 아닌 개발자 확인 필수) |
| 로컬 실행 환경 | `infra/local/`, `Makefile` | 메인 개발자 |

담당자가 바뀌면 이 표를 고친다. 요금제가 CODEOWNERS 를 지원하면 이 표를 `CODEOWNERS` 로 옮겨 리뷰 요청을 자동화한다.

## 3. 충돌을 막는 규칙

| 상황 | 규칙 |
|---|---|
| 공통 테이블을 두 기능 이상이 쓴다 | [DB 스키마 정의](../specs/db-schema.md)에서 확정한 뒤 구현한다. 확정 후 바꿀 때는 명세와 [결정 기록](../decisions/README.md)부터 고치고 스키마 소유자 리뷰를 받는다 |
| 마이그레이션 순번이 겹친다 | 파일은 `NNNN_<slug>.py` 4자리 순번. **먼저 머지한 쪽이 번호를 갖는다.** 뒤에 머지하는 쪽이 main 을 받은 뒤 번호와 `down_revision` 을 고친다. 고친 결과는 unit 테스트(`test_migration_chain.py`)가 검사한다. 마이그레이션이 든 PR 은 스키마 소유자가 리뷰한다 |
| 등록 지점을 여럿이 동시에 고친다 | `router.py` `_DOMAIN_ROUTERS`, `model_registry.py`, 오류 code 목록(`error_contract.py`·`error-messages.ts`), `pages-config.tsx` 는 **한 줄 추가만**. 충돌이 나도 두 줄 다 남기면 끝난다(생성 파일은 `make gen-error-codes` 로 다시 만든다) |
| 같은 오류를 다른 code 로 만든다 | 새 code 를 만들기 전에 `error_contract.py` 목록에서 같은 뜻의 code 를 먼저 찾는다 |
| 같은 모양을 두 사람이 다르게 만든다 | 새 화면은 **레퍼런스 슬라이스와 기존 공통 컴포넌트를 먼저 찾아** 따른다(frontend/CLAUDE.md 6단계). 없으면 기능 PR 에서 추가하되, 다른 개발자의 열린 PR 에 같은 용도가 있는지 확인하고 본문에 「공통 부품 추가」를 적는다 |
| 각자의 AI 가 다르게 판단한다 | 규칙은 **CLAUDE.md·skill 에만** 둔다. 개인 프롬프트·개인 메모에 규칙을 두지 않는다. 새 규칙이 생기면 그 문서를 고치는 PR 을 먼저 올리고 다른 개발자에게 알린다 |
| 개인 설정이 섞인다 | 팀 공용 권한은 `.claude/settings.json`(커밋), 개인 설정은 `.claude/settings.local.json`(커밋 안 함) |
| 브랜치가 오래 산다 | PR 은 작게(기능 하나), **하루 한 번 이상 main 을 받아** 충돌을 일찍 본다 |
| 같은 일을 둘이 한다 | 착수 전에 Issue 를 만들거나 찾아 담당자를 적는다(아래 6) |

## 4. 하루 작업 흐름

```
Issue 확인 — 6절 기준에 해당하면 만들거나 찾고 담당자 기입
  → 브랜치 생성: feature/<번호>-<주제> · fix/<번호>-<주제> · chore/<주제> …  (규칙은 5절)
  → Claude 에게 기능 설명 + feature-slice skill 로 진행
  → verify skill 의 검사 통과
  → (필요할 때) 자기 변경 리뷰(pre-pr-review 기준. 작성 맥락 없이 보려면 pr-reviewer 에이전트), 지적을 코드로 확인해 반영
  → PR (본문: 무엇을·왜·확인한 것·남은 것)
  → AI 리뷰(자동) + 작성자가 아닌 개발자 리뷰
  → merge commit 으로 머지
```

- **다른 사람의 PR 을 리뷰할 때**도 Claude 에게 `pre-pr-review` 기준(또는 `pr-reviewer` 에이전트)으로 먼저 보게 하고, 지적을 사람이 확인해 코멘트한다.
  AI 지적은 틀릴 수 있다 — 코드로 확인한 것만 남긴다.
- PR 하나는 리뷰어가 30분 안에 읽을 크기를 목표로 한다. 넘으면 나눈다(예: 마이그레이션+API / 화면).

## 5. git 규칙

사람과 AI 가 모두 같은 형식으로 남기도록 정한다. AI 에게 커밋·브랜치를 맡길 때도 이 절을 따른다.

### 브랜치 — main 하나 + 짧게 쓰고 지우는 작업 브랜치

영구 브랜치는 `main` 하나다. **환경별 브랜치(dev·stg·prod)를 두지 않는다** — 환경마다 무엇을 배포했는지는 아래
「배포와 태그」의 태그가 기록한다. 환경별 브랜치는 stg 에만 들어간 수정, prod 에서 직접 고친 수정을
만들어 브랜치끼리 cherry-pick 으로 맞추는 일을 부른다.

| 접두어 | 언제 | 예 |
|---|---|---|
| `feature/` | 기능 추가·변경 | `feature/user-list` |
| `fix/` | 버그 수정 | `fix/app-role-cast` |
| `refactor/` | 동작은 같고 구조만 바꿈 | `refactor/error-code-table` |
| `chore/` | 설정·문서·의존성·빌드·인프라 | `chore/git-rules` |
| `hotfix/` | 배포본 긴급 수정. 배포 태그에서 딴다(「배포와 태그」) | `hotfix/total-calc-null` |
| `claude/` | Claude Code 가 worktree 로 만든 작업 브랜치 | `claude/user-list-a1b2c3` |

- 주제는 **영문 소문자 kebab-case**, 짧게.
- **Issue 가 있는 작업은 브랜치 이름에 번호를 붙이고**(`feature/12-user-list`), 그 브랜치에서는 그 Issue 하나의 일만 한다.
  `feature/`·`fix/` 는 번호가 필수다. 번호 없는 브랜치는 Issue 를 만들지 않는 작은 `chore/`·`refactor/`(6절)만 쓴다.
- 브랜치 하나 = PR 하나. 며칠 안에 머지하고, 머지 후 지운다.
- `main` 에서 직접 커밋하지 않는다(첫 커밋 제외). main 으로 가는 push 와 force push 는 로컬 `pre-push` hook 이 막는다
  (`.githooks/`, `make setup` 이 켠다 — 요금제에 따라 서버 쪽 브랜치 보호가 적용되지 않을 수 있어서다, 7절).

### 커밋 메시지

```
<종류>: <제목 — 무엇을 바꾸는지, 한국어 현재형 한 문장>

<본문: 코드만으로 이유가 안 보일 때만. 왜 — 원인, 버린 대안, 외부 제약, 관련 기록>
```

| 종류 | 언제 |
|---|---|
| `feat` | 기능 추가·변경(사용자에게 보이는 동작) |
| `fix` | 버그 수정 |
| `refactor` | 동작은 같고 구조만 바꿈 |
| `test` | 테스트만 추가·수정 |
| `docs` | 문서만 |
| `chore` | 설정·의존성·빌드·인프라 |

- **종류는 모든 커밋에 붙인다**(머지 커밋 제외). 이 6개 밖의 종류를 만들지 않는다. 애매하면 사용자에게 보이는 동작이
  바뀌면 `feat`, 잘못된 동작을 바로잡으면 `fix`.
- 영역 괄호(`feat(users):`)는 쓰지 않는다 — 도메인 폴더 구조라 바뀐 경로가 영역을 말하고, 영역 이름이 사람마다 갈라진다.
- 제목은 `~한다` 로 끝나는 한 문장, 마침표 없음.
- **본문은 diff 가 말해 주지 않는 「왜」만** 적는다. 원인, 검토하고 버린 대안, 외부 제약(라이브러리·인프라·외부 요청),
  관련 결정 기록·Issue 번호. 2~4줄. 길어지면 결정 기록이나 PR 본문으로 옮기고 번호만 남긴다.
- 적지 않는 것: diff 를 풀어 쓴 설명("A 파일의 B 함수를 수정함"), 작업 과정("처음엔 X 를 해봤는데…").
- **예외 — 초기 구성·대량 추가 커밋**: 파일이 많아 diff 로 전체가 보이지 않는 커밋(저장소 첫 구성, 모듈 통째 추가 등)은
  본문에 **구성 요약**(무엇이 들어 있는지)을 둔다. 이 경우 구성 요약이 diff 가 말해 주지 못하는 정보다.
- 판단 기준: 6개월 뒤 다른 사람이나 AI 가 이 커밋을 보고 **되돌려도 되는지 판단할 수 있는가.**
- **AI(Claude Code)가 작성에 참여한 커밋은 마지막 줄에 공동 작성자 표시를 남긴다**(빈 줄 뒤 `Co-Authored-By: Claude <모델명> <noreply@anthropic.com>`).
  Claude Code 가 커밋할 때 붙이는 줄을 지우지 않는다. 사람이 직접 쓴 커밋에는 붙이지 않는다. 이력에서 AI 참여 커밋을 구분하는 데 쓴다.

예 — 버그 수정(원인이 코드에 안 보임):

```
fix: 앱 DB 계정 생성 SQL 의 파라미터를 text 로 형변환한다

PostgreSQL format() 은 가변 인자의 타입을 추론하지 못해
asyncpg 로 바인드하면 "could not determine data type of parameter $1"
오류로 마이그레이션이 실패했다. CAST(:x AS text) 로 타입을 명시한다.
```

예 — 설계 선택(다른 방법도 있었음):

```
refactor: 환경변수 이름을 배포 환경과 같게 접두어 없이 읽는다

배포 환경이 이미 DB_HOST·APP_ENV 로 값을 넣고 있어
접두어를 붙이면 배포 설정과 앱 사이에 이름 변환이 하나 더 생긴다. 결정 기록 0002.
```

예 — 외부 사정:

```
chore: 테스트 클라이언트 의존성을 httpx 에서 httpx2 로 바꾼다

Starlette TestClient 가 httpx 사용에 폐기 예정 경고를 내고 httpx2 설치를 안내한다.
```

예 — 본문이 필요 없음: `feat: 사용자 목록 API 를 추가한다`, `fix: 시스템 상태 화면의 오타를 고친다`,
`docs: git 규칙에 배포 태그를 추가한다`

이력에서 종류별로 보기: `git log --oneline --no-merges | grep ' feat: '`

### 커밋 단위

- 커밋 하나하나가 **검사(`make verify`)를 통과하는 상태**가 되게 나눈다.
- 마이그레이션은 별도 커밋으로 두면 순번 충돌을 고칠 때 편하다.
- 포맷만 바꾸는 변경과 동작을 바꾸는 변경을 한 커밋에 섞지 않는다.

### main 받기와 머지

- 작업 중 main 을 받을 때는 **merge** 한다(`git merge main`). 이미 공유한 브랜치를 rebase 로 고쳐 쓰지 않는다
  (force push 는 로컬 `pre-push` hook 이 막고, `.claude/settings.json` 이 AI 의 force push·hook 우회를 막는다).
- PR 머지는 **merge commit** 이다. squash 하지 않는다 — 커밋 단위의 「왜」가 이력에 남아야 한다.
- main 을 받은 뒤에는 `make verify` 를 다시 돌린다. 머지로 들어온 파일이 내 변경과 부딪힐 수 있다.

### 배포와 태그

배포 방식(대상 환경 · 빌드 · 인프라)은 프로젝트에서 정하고, 정하면 이 절에 적는다. 정하기 전에도 아래 원칙은 지킨다.

- 환경마다 무엇을 배포했는지는 **배포한 main 커밋에 붙인 태그**로 남긴다. 태그 이름: `deploy/<환경>-<YYYYMMDD><NN>` — NN 은 하루 안의 순번.
  예: `deploy/stg-2026112001`.
- 태그는 배포 담당자가 배포 직후에 붙인다(`git tag -a deploy/stg-2026112001 -m "<무엇을 배포했나>"` → `git push origin <태그>`).
  붙인 태그는 옮기거나 지우지 않는다.

**배포본에 급한 수정이 필요한데 main 에 아직 배포하지 않을 변경이 쌓여 있으면:**

1. 그 환경의 마지막 배포 태그에서 `hotfix/<주제>` 를 딴다: `git switch -c hotfix/total-calc-null deploy/stg-2026112001`
2. 고치고 검사·리뷰를 거쳐 그 브랜치에서 배포한 뒤 새 배포 태그를 붙인다.
3. **같은 수정을 main 에 머지한다**(빠뜨리면 다음 배포에서 버그가 되살아난다). 그다음 hotfix 브랜치를 지운다.

main 이 그대로 배포 가능한 상태면 hotfix 브랜치 없이 main 에서 평소대로 고쳐 배포한다.

환경별 브랜치를 다시 검토하는 경우는 하나다 — 외부 QA 가 stg 에서 몇 주간 검수하는 동안 그 버전을 고정해야 하는데
main 은 계속 나아가야 할 때. 그때도 영구 브랜치가 아니라 `release/<버전>` 을 짧게 두고 QA 가 끝나면 지운다.

### PR

- 제목은 커밋 제목과 같은 형식(`feat: …`). 본문은 **무엇을 · 왜 · 확인한 것(돌린 검사와 결과) · 남은 것**. 화면 변경이면 스크린샷.
- 본문에 `Closes #번호`(그 Issue 를 끝내는 PR) 또는 `Refs #번호`(같은 Issue 의 중간 PR)를 적는다. Issue 가 없는 작은 작업이면
  `Issue 없음 — 작은 정리` 라고 적는다(빈칸으로 두지 않는다).
- **작성자가 아닌 개발자 1명 이상을 리뷰어로 지정한다.** Claude 는 CLAUDE.md 의 개발자 표로 지정하고, 웹에서 직접 만들 때는 사람이 지정한다.
  GitHub 요금제에 따라 비공개 저장소에서 팀 리뷰어·CODEOWNERS 를 쓸 수 없으면 사람(또는 Claude)이 직접 지정한다.
- draft 로 올리지 않고 리뷰 가능한 상태로 올린다.

## 6. 작업 추적

작업은 GitHub Issue 로 추적한다. **Issue 하나 = 작업 하나**이고, 한 Issue 에 브랜치·PR 이 여러 개 붙을 수 있다
(중간 PR 은 `Refs #`, 마지막 PR 은 `Closes #`). 저장소 안에 별도 TODO 파일·백로그 문서를 만들지 않는다.

### Issue 를 만드는 기준 — 하나라도 해당하면 만든다

| 기준 | 예 |
|---|---|
| 기능 추가·변경(`feature/`), 버그 수정(`fix/`) | 사용자 목록 화면, 합계 계산 오류 |
| 계약을 건드린다 — DB 스키마·API·공통 영역(2절)·규약 문서 | 공통 테이블 추가, CLAUDE.md 규칙 변경 |
| PR 이 2개 이상이거나 하루를 넘긴다 | 파일 업로드와 비동기 처리 |
| 지금 하지 않고 미룬다 | 리뷰 지적 중 이번 범위 밖인 것, 기획 확인 대기 |

**만들지 않는 것**: 위 어디에도 해당하지 않고 PR 하나로 그날 끝나는 작은 `chore/`·`refactor/`(오타·문구·이름 정리 등).
번호 없는 브랜치로 하고 PR 본문에 `Issue 없음 — 작은 정리` 라고 적는다.

### 빠뜨리지 않는 장치

- **브랜치 이름**: `feature/`·`fix/` 는 번호가 필수라, 브랜치를 만드는 순간 Issue 가 걸러진다(5절).
- **Claude 가 시작할 때 확인**: 작업을 시작할 때 위 기준으로 판단해, 필요한데 없으면 **기본값으로 만들고** 번호를 알린다.
  사용자가 「Issue 없이」라고 할 때만 생략한다.
- **미룬 일은 그 자리에서**: 「나중에」로 넘기는 일은 대화·로컬 메모에 두지 않고 바로 `deferred` Issue 로 만든다.
- **PR 본문 연결 칸**: `Closes`·`Refs` 또는 `Issue 없음 — 작은 정리` 를 반드시 적는다(5절 「PR」).

### 라벨·마일스톤

- 상태 라벨: `triage`(조사·판단 필요) · `ready`(착수 가능) · `deferred`(보류). 종류는 브랜치 접두어가 말해 주므로 따로 두지 않는다.
  **상태 라벨은 Issue 에만 붙인다.** PR 의 상태(열림·리뷰·머지)는 GitHub 가 보여 준다. 작업 중인지는 담당자와 연결된 PR 로 본다.
- 마일스톤: 오픈 단위(`1차 오픈` 등 프로젝트에서 정한다). 그 오픈에 들어갈 Issue 에 붙여 남은 일을 본다.

## 7. GitHub 구성

| 항목 | 내용 |
|---|---|
| `.github/workflows/ci.yml` | backend ruff·pyright·pytest(unit + integration — `make local-up` 으로 로컬과 같은 Postgres · S3 호환 스토리지 컨테이너), frontend `npm run verify`. PR 마다, 그리고 main 에 들어간 뒤 실행. 검사 목록을 바꾸면 루트 `Makefile` 의 verify 대상·verify skill 과 함께 고친다 |
| `.github/workflows/ai-review.yml` | PR 이 열리면(초안 해제 포함) Claude Code 가 `pre-pr-review` skill 기준으로 인라인·요약 코멘트를 단다. **PR 당 한 번**이고 커밋을 더 올려도 다시 돌지 않는다 — 다시 받으려면 PR 코멘트 `/review`(쓰기 권한자). 코드 경로가 바뀐 PR 만 자동 실행하고 문서만 바뀐 PR 은 `/review` 로만. 빼려면 PR 을 만들 때 라벨 `skip-ai-review`. 토큰은 저장소 시크릿 `CLAUDE_CODE_OAUTH_TOKEN` 하나다(아래). 시크릿이 없으면 잡이 그 이유를 적고 실패한다. 마지막 스텝이 실행 기록을 읽어 리뷰 미완료를 실패로 바꾼다. **이 워크플로 파일을 바꾸는 PR 에서는 액션이 실행을 건너뛰어 잡이 붉게 보인다**(PR 의 워크플로가 main 과 같아야 한다는 액션의 안전장치) — 머지 뒤 `/review` 로 확인한다 |
| PR 템플릿 | 무엇을·왜·확인한 것·남은 것·AI 리뷰(전체 / 코드만 / 생략)·Issue 연결 칸(6절) |
| 라벨 | `triage` · `ready` · `deferred`(6절), `skip-ai-review`. 저장소를 만든 뒤 한 번 만든다(`gh label create <이름>`) |
| `CODEOWNERS` | 위 2의 소유 표. 요금제가 지원하면 옮긴다 |
| 브랜치 보호 | main 직접 push 금지, CI 통과 + 리뷰 1명 필수. 요금제에 따라 비공개 저장소에 룰셋이 적용되지 않을 수 있다 — 그래도 룰셋은 만들어 두고, main 직접 push·force push 는 로컬 hook(`.githooks/pre-push`)이 막는다 |

### AI 리뷰 토큰 등록

필요한 시크릿은 **`CLAUDE_CODE_OAUTH_TOKEN` 하나**다. 리뷰 사용량은 이 토큰을 만든 Claude 계정의 구독에서 나간다.

1. 토큰을 낼 사람(보통 메인 개발자)이 `claude setup-token` 을 실행해 토큰을 만든다. 토큰은 1년 유효하고, 폐기는 claude.ai → Settings → Claude Code.
2. 저장소에 시크릿으로 넣는다 — `gh secret set CLAUDE_CODE_OAUTH_TOKEN`(값을 붙여 넣는다) 또는 GitHub 저장소 → Settings →
   Secrets and variables → Actions → New repository secret.
3. 확인: 코드가 바뀐 PR 을 열거나 PR 에 `/review` 코멘트를 달아 AI Review 잡이 초록으로 끝나는지 본다.

토큰을 바꿀 때도 같은 이름으로 다시 `gh secret set` 한다.

# 0001. 기능별 풀스택 분담 — 백엔드 공통은 소유자, 프론트는 소유자 없이 함께

2026-11-09 · 상태: 확정

## 배경

여러 개발자가 각자 AI(Claude Code)로 개발한다. 개발자의 경험이 한쪽(백엔드 등)에 치우쳐 있을 수 있고, 화면은 별도 담당자가
목업 HTML 로 전달하기도 한다. 일정이 짧으면 서로 기다리는 시간을 줄여야 한다.

## 결정

- 백엔드/프론트엔드가 아니라 **기능(도메인) 단위로 나눠** 한 사람이 DB·API·화면·테스트를 끝까지 만든다.
- 기반(골격·DB 스키마 정의·API 명세·레퍼런스 구현 1개)은 **메인 개발자가 먼저 만들고**, 그 위에서 기능을 나눈다.
- **백엔드 공통 영역은 소유자 한 명**을 둔다 — DB 스키마 · 마이그레이션 체인, 백엔드 공통(`api` · `db` · `middleware` · `core` ·
  config · logging · main), 공통 테이블 모델. 소유자가 아닌 사람이 바꿔야 하면 그 변경만 작은 별도 PR 로 먼저 올린다.
- **프론트 영역은 소유자를 두지 않는다** — 화면 기능 정의 · 목업 원본, 공통 컴포넌트 · 스타일 · 디자인 정의, 셸 · 라우팅 · API
  전송 계층. 화면을 만드는 사람이 기능 PR 안에서 함께 고친다.
- **예외: 인증 · 권한**(백엔드 인증과 프론트의 인증 상태 · 로그인 화면 · 401 처리)은 묶인 기능이라 인증 · 권한 담당자 소유로 둔다.
- **공통 부품 중복 방지**: 공통 부품(`components/` · `lib/` · `styles/` 의 공용 클래스 · `api/` 의 공용 타입)을 새로 만들 때는 다른
  개발자의 열린 PR 에 같은 용도가 있는지 먼저 확인하고, PR 본문에 「공통 부품 추가: 무엇」을 적는다. 리뷰어가 그 줄로 중복을 본다.
- **기획 반영은 메인 개발자** — 새 기획 · 시안 결정을 기획 문서 · 명세로 옮기는 일. 화면을 만들며 생기는 세부
  보완(문구 · 빈 상태 · 시안과 다르게 가는 이유)은 그 화면을 만드는 사람이 같은 PR 에서 고치고, PR 본문에 「기획 보완: 문서 · 절 —
  무엇」을 적어 메인 개발자가 볼 수 있게 한다.

상세 규칙은 [collaboration.md](../development/collaboration.md).

## 근거

- 백엔드/프론트 분할이면 누군가 경험이 적은 영역을 전담하게 되고, API 명세가 나오기 전까지 프론트가 막힌다.
- 기능별 분할은 메뉴 단위 완성(기능이 완성되는 PR 이 그 메뉴를 「준비 중」에서 연다 — 결정 0003)과 맞고, 대기 시간이 거의 없다.
- 백엔드 공통은 순번 충돌(마이그레이션)과 공통 테이블처럼 한 사람이 일관성을 지켜야 하는 것이라 소유자를 둔다.
- 프론트는 화면을 만들 때마다 공통 컴포넌트 · 스타일 · 디자인 정의를 함께 고치게 된다. 소유자를 두면 그때마다 별도 PR 이 생겨 화면 하나가
  PR 여러 개로 쪼개지고 서로를 기다린다. 소유로 막으려던 위험 중 패턴 분화는 레퍼런스 화면과 frontend/CLAUDE.md 의 순서가, 공통 부품
  중복은 PR 본문 기재와 리뷰가 막는다 — 중복은 소유자가 있어도 서로의 열린 PR 을 몰라서 생기므로, 막는 것은 「열린 PR 을 보는 것」이다.

## 영향

- 명세는 `docs/specs/`(DB 스키마·API)에 두고, 구현된 뒤에는 코드가 정본이다.
- 코드 구조를 도메인 폴더 단위로 둔다: `backend/app/domains/<domain>/`, `frontend/src/api/<domain>/`, `frontend/src/app/pages/<domain>/`.
- 여러 사람이 함께 고치는 등록 지점은 한 줄 추가만 한다.
- `docs/development/collaboration.md` 2절 소유 표 · 3절, `CLAUDE.md` 「작업 범위와 분담」, `frontend/CLAUDE.md`,
  `.claude/skills/feature-slice` · `pre-pr-review` 체크리스트, PR 템플릿.

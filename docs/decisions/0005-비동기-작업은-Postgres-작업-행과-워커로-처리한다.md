# 0005. 비동기 작업은 Postgres 작업 행과 워커로 처리한다 — 별도 메시지 큐를 쓰지 않는다

2026-11-09 · 상태: 확정

## 배경

업무 시스템의 비동기 작업은 보통 업로드 파일 검사, 건별 처리(수백 건 단위), 외부 시스템 전달과 재조회(주기 · 상한), 외부 API 호출
(동시 호출 제한), 재시도, 만료 데이터 정리다. 처리량은 하루에 몇 번 수준이고, 한동안 쓰이지 않는 기간도 있다.
메시지 큐 서비스(SQS 등)를 두는 방법도 있다.

## 결정

- 비동기 작업은 **전부 Postgres 작업 행 + 워커 프로세스**(`python -m app.worker`)로 처리한다. 별도 메시지 큐는 쓰지 않는다.
- 즉시형 작업: 작업 행을 `SELECT … FOR UPDATE SKIP LOCKED` 로 집는다. API 가 행을 커밋한 뒤 `NOTIFY` 를 보내고 워커는 전용 접속으로
  `LISTEN` 해 즉시 깨어난다. 알림 유실에 대비한 보조 폴링은 60초(설정값).
- 예약형 작업(재조회 · 재시도 · 정리): 행에 `next_attempt_at` 을 두고 워커 타이머가 집는다. 외부 호출 작업은 시도 횟수와
  마지막 오류를 행에 남긴다.
- 처리는 멱등이다. 집힌 뒤 일정 시간이 지나도 끝나지 않은 행은 워커가 죽은 것으로 보고 다시 큐에 넣으며 시도 횟수를
  올린다. 상한을 넘으면 실패로 둔다.
- 워커는 결과를 DB 에 직접 쓴다(API 호출·이벤트 발행 없음). 여러 작업 행이 끝나야 끝나는 묶음(부모 행)은, 끝난 건수를 원자적으로
  올려(`UPDATE … SET done_count = done_count + 1 … RETURNING`) 전체에 닿게 한 워커만 부모를 완료로 바꾼다 — 「안 끝난 행이 없는가」
  조회는 마지막 두 건을 동시에 끝낼 때 서로의 미커밋 행을 보고 둘 다 완료를 놓친다.
- 워커 한 프로세스 안의 동시 처리 수는 소비자마다 세마포어(설정값), 프로세스 수는 배포 설정이 정한다.
- 공용 틀은 `backend/app/worker/` 이고 작업 함수는 도메인 폴더에 둔다. 소비자 · 주기 작업은 `app/worker/__main__.py` 의 `CONSUMERS` · `PERIODIC` 에 한 줄씩 더한다.

## 근거

- 이 처리량에서 메시지 큐가 주는 것(서비스 간 분리, 대량 버퍼, 서버리스 트리거)은 쓰이지 않고, 로컬에 대체 컨테이너와
  최소 1회 전달에 대한 멱등·재전달 처리만 더해진다. 작업 목록은 어차피 DB 행이라 큐가 둘이 된다.
- 큐 소비도 롱 폴링이라 즉시성은 `LISTEN/NOTIFY` 를 붙인 Postgres 큐와 다르지 않다. 보조 폴링을 60초로 두면 유휴
  기간의 조회 비용은 1분 1회 인덱스 조회다.
- `LISTEN/NOTIFY` 는 Postgres 코어 기능이고 Graphile Worker·Oban 등 작업 큐 라이브러리가 같은 구조로 운영된다.
  주의할 조건은 트랜잭션 단위 커넥션 풀러(PgBouncer transaction 모드 등)를 거치면 `LISTEN` 이 동작하지
  않는다는 것뿐이다. 풀러를 도입하면 알림 접속만 우회시킨다.
- 처리량이 가정보다 수십 배 커지거나 외부 콜백 버퍼가 필요해지면 집는 부분만 메시지 큐로 바꾼다. 행 구조는 그대로다.

## 영향

- 작업 큐가 되는 테이블은 `attempt`·`claimed_at` 과 대기 상태 부분 인덱스를 갖는다(api.md 「워커」).
- 로컬 개발에 큐 대체 컨테이너가 필요 없다.

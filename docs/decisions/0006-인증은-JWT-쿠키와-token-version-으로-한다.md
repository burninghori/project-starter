# 0006. 인증은 자체 계정 + JWT 쿠키 + token_version 매 요청 대조로 한다

2026-11-09 · 상태: 확정

## 배경

업무 시스템은 보통 시스템 자체 계정(ID·비밀번호)과 사용자 등록을 전제한다. 사용자 규모는 수십 명 안팎이고,
비활성화·비밀번호 초기화가 즉시 먹어야 한다. SSO 요구가 생기면 이 결정을 다시 본다.

## 결정

- 시스템 자체 계정. 비밀번호는 **bcrypt 해시**로 저장한다(라이브러리 래퍼 없이 `bcrypt` 패키지를 직접 쓴다). 규칙은 8자 이상 ·
  UTF-8 72바이트 이하(bcrypt 입력 상한) · 공백 금지 · 조합 요구 없음이고, 검증 함수 하나가 정본이다. 72바이트를 넘는 로그인
  시도는 오류가 아니라 불일치로 답하되, 응답 시간으로 계정 존재가 드러나지 않게 해시 검증을 한 번 수행한다.
- 관리자가 비밀번호 값을 정하지 않는다. 사용자 생성·관리자 초기화는 서버가 무작위 임시 비밀번호를 발급하고(로그에 남기지 않는다)
  `must_change_password` 를 켠다.
- 세션은 백엔드가 발급하는 JWT(HS256, `JWT_SECRET`)를 **httpOnly 쿠키**(SameSite=Lax)에 싣는다. 리프레시 토큰은 없다.
  만료는 설정값.
- 토큰에는 사용자 ID 와 발급 시점 `token_version` 만 싣고 역할은 넣지 않는다. **매 요청 DB 에서 활성·`token_version`·역할을
  읽어 대조**한다. 불일치면 401.
- `token_version` 증가: 비활성화·관리자 비밀번호 초기화·세션 회수는 무조건 `+1`(그 사용자의 모든 쿠키 무효), 본인
  비밀번호 변경은 기대 버전 조건부 `+1`(자기 쿠키 재발급).
- 관리자 초기화 뒤에는 `must_change_password` 가 켜지고, 그동안 `/auth/me`·`/auth/logout`·`/auth/password` 외 요청은
  403.
- **로그인 잠금**: 같은 계정의 연속 실패가 `LOGIN_MAX_FAILURES` 에 닿으면 `LOGIN_LOCK_MINUTES` 동안 비밀번호를 보지 않고 429 로 답한다.
  계정 단위이고(`app_user.failed_login_count` · `locked_until`, 여러 인스턴스가 같은 DB 를 본다), 출처(IP) 단위 제한은 앞단(프록시 · WAF)의 일이다.
  관리자 비밀번호 초기화가 잠금을 푼다. 로그인 거부와 잠금은 `warning` 로그로 남긴다.
  잠금 판정은 실패 기록 · 성공 정리의 UPDATE 가 행 잠금 아래에서 하므로, 같은 계정에 동시에 보낸 시도도 한도를 넘어 결과를 알려 주지 않는다.
  대가 둘을 알고 택한다: 잠긴 계정의 429 는 계정이 있다는 것을 드러내고, 아이디를 아는 사람은 누구든 그 계정을 잠금 시간 동안 잠글 수 있다
  (잠금 남용). 관리자가 한 명이면 그 동안의 복구 수단은 명령 `reset_password` 다. 남용이 문제가 되면 앞단의 출처 단위 제한을 먼저 붙인다.
- **CSRF**: 쿠키의 SameSite=Lax 에 더해, 쓰기 요청(GET · HEAD · OPTIONS 가 아닌 것)의 `Origin` 을 `ALLOWED_ORIGINS`(화면이 열리는 출처)와
  대조해 밖이면 403 이다. Lax 는 같은 사이트의 다른 출처(서브도메인 · 같은 등록 도메인의 다른 앱)에서 온 요청에는 쿠키를 싣기 때문이다.
  `Origin` 이 없는 요청은 브라우저가 아니므로 통과시킨다. 토큰 방식(double submit)은 쓰지 않는다 — 화면과 API 가 같은 출처라 출처 대조로 충분하고 부품이 적다.
- **로그아웃은 쿠키만 지운다.** 서버에 세션 상태가 없으므로, 로그아웃 전에 빼낸 토큰은 만료(`JWT_TTL_MINUTES`)까지 유효하다.
  로그아웃 때 `token_version` 을 올리면 막을 수 있지만 그 사용자의 다른 기기도 함께 끊긴다 — 필요해지면 이 결정을 고친다.
- 역할 → 메뉴·기능 표는 코드가 갖는다. 역할 목록·기능 권한은 프로젝트의 기획이 정해지면 채운다.

## 근거

- 매 요청 DB 를 보므로 즉시 무효화가 보장된다. 요청당 PK 조회 1회라 이 규모에서 부담이 아니다.
- 검토한 대안: 불투명 세션 ID + 세션 표 — 부품은 적지만 기능이 같고, 같은 구조로 운영 중인 참고 구현을
  그대로 쓸 수 있는 쪽이 공수가 적다. WebSocket·서명 URL 이 생겨도 같은 키로 확장된다.
- 토큰 값을 믿고 DB 조회를 없애는 방식(무상태 JWT, 짧은 만료 + 리프레시, 프로세스 내 캐시)은 즉시 무효화를 잃거나 인스턴스 간
  동기화 문제를 만든다. 필요해지면 미들웨어 안의 캐시로 뒤에 붙일 수 있는 구현 세부라 지금 정하지 않는다.

## 영향

- `app_user`: `password_hash`·`token_version`·`must_change_password`·`is_active`·`role`·`failed_login_count`·`locked_until`(db-schema 「app_user」).
- API: `POST /auth/login`·`/auth/logout`·`/auth/password`, `GET /auth/me`(api.md 「인증」), 관리자용 `/users`(api.md 「사용자 관리」 — 생성 · 수정 · 사용 중지 · 초기화).
  활성 관리자는 늘 한 명 이상 남는다(마지막 관리자의 강등 · 사용 중지는 409) — 관리자가 0명이 되면 앱 안에서 되돌릴 길이 없다.
  사용자 관리 화면은 프로젝트에서 만든다. 첫 관리자는 명령 `seed_admin`, 관리자가 자기 비밀번호를 잊었을 때는 명령 `reset_password` 로 한다.
- 설정: `JWT_SECRET`(32바이트 이상, 배포 환경은 비밀 저장소로 넣는다) · `JWT_TTL_MINUTES` · `COOKIE_SECURE` · `LOGIN_MAX_FAILURES` · `LOGIN_LOCK_MINUTES` · `ALLOWED_ORIGINS`.
- 의존성: `bcrypt`.

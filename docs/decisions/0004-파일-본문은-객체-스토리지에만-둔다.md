# 0004. 파일 본문은 객체 스토리지에만 두고 DB 에는 메타·해시·키만 둔다

2026-11-09 · 상태: 확정

## 배경

사용자가 올리는 파일(문서 · 이미지 · JSON 등)은 건당 수십 KB 에서 수 MB 이고 계속 쌓인다. 본문을 DB(bytea · JSONB)에 두면
처리와 조회를 한 트랜잭션 안에서 할 수 있지만, 백업 · 복원 크기와 목록 조회에서 본문을 실수로 읽는 비용이 커진다.

## 결정

- 파일 본문은 **S3 호환 객체 스토리지(`STORAGE_BUCKET`)에만** 둔다. DB 에는 메타(이름 · 종류 등) · 원본 바이트 해시 · 객체 키 · 크기만 둔다.
- 객체는 덮어쓰지 않는다 — 교체는 새 키다. 저장은 조건부(`If-None-Match: *`)라 같은 키가 이미 있으면 실패한다. 옛 행이 가리키는 본문이
  그대로 보존된다.
- 키 규칙의 정본은 `backend/app/core/storage.py` 의 키 함수다. 기능이 키 함수를 더할 때는 정리 단위(접두사째 지울 묶음)를 키의 앞쪽에 둔다.
  DB 를 다시 만들어 id 가 다시 시작할 수 있으면 키에 무작위 토큰을 넣어 남아 있는 옛 객체와 겹치지 않게 한다.
- 로컬 개발은 docker-compose 에 S3 API 호환 컨테이너(SeaweedFS)를 두어 같은 코드 경로 하나로 간다(boto3 + `endpoint_url` + path-style, 로컬·배포는 환경변수만 다르다).
  SeaweedFS 로 확인한 것: boto3 path-style 접속 · `HeadBucket`(있으면 200, 없으면 404) · 조건부 저장 `If-None-Match: *`(같은 키면 412 PreconditionFailed 로 거부, 기존 객체 보존) ·
  스트림 GET · 삭제 뒤 같은 키 재저장 · 마스터 `/dir/assign` 헬스체크(쓸 수 있는 볼륨까지 확인) · 기동 때 `weed shell s3.bucket.create` 로 버킷 생성(멱등) ·
  `-s3.autoCreateBucket=false` 로 없는 버킷에 저장하면 NoSuchBucket 으로 실패(버킷 이름 오타가 조용히 새 버킷을 만들지 않는다). CI 도 같은 compose 파일을 띄운다.
- presigned URL 은 쓰지 않는다. 원본 내려받기는 API 가 객체를 읽어 스트림으로 내려준다 — 쿠키 인증이 그대로 적용되고 스토리지 주소가 브라우저에 노출되지 않는다.
- 업로드를 「올림 → 확정」 두 단계로 나누는 기능은, 확정되지 않은 객체를 워커의 주기 작업(결정 0005)이 만료 기한 뒤 접두사째 지운다. API 서버는 정리를 하지 않는다.

## 근거

- 파일 본문을 읽는 곳은 보통 처리 작업(워커)과 내려받기뿐이다. 목록 · 상세는 메타만 보인다.
- JSONB 는 키 순서·중복 키를 보존하지 않아 원본으로 쓸 수 없고, 큰 값이 쌓이면 백업·복원 크기와 목록 조회에서
  본문을 실수로 읽는 사고 비용만 커진다.
- 검토한 대안: DB 본문 — 위 이유로 기각.

## 영향

- 파일을 다루는 테이블은 `storage_key`·`size_bytes`·`content_sha256` 을 갖고 본문 칼럼을 두지 않는다.
- 코드 경로는 `backend/app/core/storage.py` 하나(put 은 조건부 저장만, get 은 스트림, 접두사 단위 삭제, 키 규칙 함수). 로컬 컨테이너는 `infra/local/docker-compose.yml`(+ `infra/local/seaweedfs/`), 안내는 `docs/development/local-setup.md`.
- `GET /api/health/ready` 가 DB 와 함께 버킷(`HeadBucket`)을 확인한다 — 스토리지에 못 붙으면 준비 안 됨.
- 업로드 경계 검사(본문 길이 · 파일 이름)는 `backend/app/api/uploads.py`, 첨부 헤더는 `app/api/downloads.py` 가 공용이다(api.md 「업로드」).
